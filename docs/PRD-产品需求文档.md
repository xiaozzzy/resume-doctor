# 简历医生产品需求文档

> 当前版本：v1.5 ｜最后更新：2026-07

## 1. 问题与目标

求职者在投递前通常无法判断简历和 JD 的差距，也很难把同一段真实经历改写成不同岗位能理解的表达。人工改简历的交付慢、单次成本高，难以覆盖“一个岗位一版简历”的投递节奏。

**产品目标：** 将投递前的“检查、改写、排版、面试准备”串成一次可完成的工作流，帮助用户得到可继续编辑的材料，而不是替用户虚构一份简历。

## 2. 目标用户

| 用户 | 典型任务 | 需要的结果 |
| --- | --- | --- |
| 应届生 | 第一次整理简历 | 找到结构、表达与量化问题 |
| 转行求职者 | 用旧经历匹配新岗位 | 判断可迁移能力与缺失项 |
| 有经验跳槽者 | 对照具体 JD 定制投递 | 快速完成一份可核对的改写初稿 |

## 3. 当前版本范围

| 模块 | 已实现 | 不在当前承诺内 |
| --- | --- | --- |
| 材料输入 | 文本粘贴、PDF 解析、图片识别 | 复杂扫描件的百分百 OCR 准确率 |
| AI 诊断 | 评分、问题、关键词、改写示范 | 代替 HR 或预测录用结果 |
| AI 改写 | 基于原文与 JD 的完整 Markdown 简历 | 虚构项目、技能、业绩或量化数字 |
| 导出 | 4 套模板、一页纸或不限页 PDF | 复杂可视化简历编辑器 |
| 面试 | 6-8 道针对性问题及答题提示 | 实时语音模拟面试 |
| 账号 | 邮箱验证码登录、基础会话 | 求职社交、简历长期云端管理 |

## 4. 核心流程与规则

1. 用户输入简历，JD 为可选项。
2. 用户登录后可使用真实模型请求；未输入内容时可进入演示模式。
3. 诊断报告必须包含可追溯的问题引用与五维评分。
4. 改写只使用简历原文中的真实材料。缺失数据以 `[X]` 标出，用户自行补充。
5. 用户可编辑改写结果，再选择模板导出 PDF，或基于同一份材料生成模拟面试题。

## 5. AI 方案与安全边界

| 风险 | 当前处理 |
| --- | --- |
| 输出格式漂移 | 诊断与面试使用 JSON 输出要求，服务端校验必要字段并清洗数组 |
| 编造经历 | Prompt 明确限制；改写中的未知数字只能输出 `[X]` |
| 建议没有依据 | 问题清单要求引用原简历句子 |
| 成本和延迟上升 | 简历和 JD 单项限制 8,000 字；限制输出 token |
| 密钥泄露 | Key 仅在 Serverless 环境变量中读取 |
| 隐私疑虑 | 不将简历作为业务数据持久化；统计接口仅提供聚合计数 |

关于登录和 Redis 降级逻辑的生产限制，见 [AI 设计说明](AI设计说明.md)。

## 6. 指标设计

当前项目未公开真实用户指标，以下为后续验证口径：

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 诊断完成率 | 进入输入页后成功看到报告的比例 | 判断主流程是否可用 |
| 改写转化率 | 完成诊断后进入改写的比例 | 判断报告是否促成下一步行动 |
| 导出率 | 生成改写后导出 PDF 的比例 | 判断结果是否被用于投递 |
| 面试题使用率 | 完成改写后打开模拟面试的比例 | 判断工作流是否形成闭环 |
| 用户反馈 | 用户是否核对并采用建议 | 验证建议的可操作性 |

## 7. 后续优先级

1. 在不保存简历全文的前提下，补齐匿名漏斗事件和失败原因统计。
2. 将改写结果增加逐条采纳/拒绝机制，避免用户只获得黑盒全文。
3. 为多模型和 OCR 能力补充明确的服务可用性检测与降级提示。
4. 在真实用户研究后，再决定是否投入多轮追问或长期简历管理。
