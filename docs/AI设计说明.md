# AI 设计说明

## 设计目标

把模型放在“辅助判断和起草”的位置，而不是让它替用户捏造简历或做录用判断。前端展示的内容必须可以回到用户输入进行核对。

## 接口与输出

| 接口 | 输入 | 输出 | 核心约束 |
| --- | --- | --- | --- |
| `analyze` | 简历、可选 JD | 分数、五维拆解、问题、缺失关键词、改写示范 | 每个问题引用原文；评分按预设档位 |
| `rewrite` | 简历、可选 JD | Markdown 完整简历 | 不增加不存在的经历、技能或数据；未知数字用 `[X]` |
| `interview` | 简历、可选 JD | 6-8 道问题、考察点、答题提示 | 项目深挖题以原简历为基础，覆盖多个题型 |
| `extract` | 图片 Data URL | 识别出的纯文本 | 只转录文本，不生成评价 |

诊断与面试优先使用 OpenAI 兼容 API 的 `response_format: { type: 'json_object' }`；不支持该参数的平台会自动重试一次。拿到模型响应后，服务端仍会解析、校验和清洗，避免未经处理的文本直接驱动页面渲染。

## 约束策略

1. **来源约束：** 诊断问题携带 `quote` 字段；改写和项目深挖题只可使用输入中已有事实。
2. **不确定性显式化：** 缺少业绩数字时输出 `[X]` 和待补充说明，不把推测写成事实。
3. **任务拆分：** 诊断、改写、面试、图片转录各用独立 Prompt，减少单一大 Prompt 同时承担太多目标。
4. **长度控制：** 简历和 JD 单项最长 8,000 字；接口限制输出 token，控制响应时间和调用成本。
5. **稳定性控制：** 诊断温度为 `0.3`，优先稳定的结构化建议；改写和面试保留适度多样性。

## 数据与隐私

- 文本 PDF 由 PDF.js 在浏览器端提取，文件本身不需要发送到应用服务端。
- 图片识别、诊断、改写和面试会将当前请求材料发送给配置的模型服务，以完成本次请求。
- 项目代码未实现简历正文的业务持久化；Redis 用于验证码、会话和聚合计数。
- `stats` 只返回用户数、诊断数、改写数等聚合数据，不返回简历或邮箱。
- 用户仍应在输入前删除身份证号、住址等非必要敏感信息，并在导出前核实所有内容。

## 访问控制和运行限制

生产环境应配置 KV 和邮箱服务，才能提供验证码、会话和基础反滥用能力。当前 `_kv.js` 在 KV 未配置或不可用时会为演示便利降级放行会话校验，这意味着它不应被当作生产级权限控制或配额控制。后续生产化应改为：KV 不可用时拒绝受保护请求，另加服务端限流、验证码发送频率限制、审计日志和数据保留策略。

## 可验证的边界

这个系统可验证的是：输入内容能否被结构化分析、建议是否引用原文、改写是否保留事实边界、输出是否能被用户继续编辑。它不能验证候选人的真实能力，更不能保证面试或录用结果。
